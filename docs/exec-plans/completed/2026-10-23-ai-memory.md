# AGE-137: ai-memory at the runner's dispatch boundary

## Goal

Give a ticket's next agent the outcome of earlier runs, whichever provider wrote them — without
installing lifecycle hooks into Claude Code/Codex/DSH and without a per-user daemon. ai-memory runs
as a repo-local service; the runner injects a bounded brief before a fresh non-confidential project
run and appends one run-summary section after it.

## Approach

`runner/ai_memory.py` is a small JSON-RPC client for ai-memory's `/mcp` endpoint plus the server
lifecycle. On first use it starts `.tools/ai-memory/ai-memory serve --transport http --enable-api
--bind 127.0.0.1:<per-checkout port> --no-watcher` with `--data-dir state/ai-memory`, waits at most 3 s for
`/healthz`, and reuses a healthy server left by a previous runner. If `config.toml` is missing the
client fails open and asks for the installer instead of running `init` inside a dispatch. `AI_MEMORY_SERVER_URL`
switches to an external server; `AI_MEMORY_AUTH_TOKEN` supplies its token.

Scope is `workspace=<project key>`, `project=<ticket id>`, page `tickets/<ident>.md`. The page is one
markdown log: a fixed H1 header and one `## run <id8> · <UTC> · <agent> · <status>` section per run.
Every section also carries a full-id marker, `<!-- agenticos-run: <full id> -->`, so idempotency never
depends on an 8-character prefix or on text inside a summary. The page header keeps a
`<!-- agenticos-runs: … -->` index of the last 100 run ids, so a retried run is still a no-op after
its section has been trimmed out of the bounded page. On a page written before the index existed,
the index is inserted into the header and seeded from the retained section markers; an index left
inside a section by the earlier build is moved out.

Writes use `memory_write_page` with `expected_page_id` (or `create_only` for the first write), so two
runs cannot silently overwrite each other; a `precondition_failed` triggers one re-read and retry.
The new section is appended first and the whole page is trimmed afterwards to both limits (40
sections, 12,000 UTF-8 bytes), so an append can never leave 41 sections. A memory HTTP call has an absolute 4 s
deadline: the request runs in a daemon worker the caller joins for exactly that long. On expiry a
cancel event is set, the socket is shut down (which unblocks any header or body read), the connection
is closed and the call fails open; the response is capped at 2 MB. Connect and request are split, so
a worker that resumes after a stalled DNS lookup sees the cancel flag and returns without sending.
At most 4 requests may be outstanding; beyond that a call fails open instead of piling up workers.
No sent request or open socket outlives a timed-out call, and no grace wait is added after the
deadline: cancelled workers finish asynchronously under the in-flight cap. A lookup already inside the
resolver may keep at most four workers waiting until it returns; each then sees the cancel flag, sends
nothing and closes what it opened, so a server that drips bytes cannot block the dispatch or the
terminal run record. Health probes have their own 1 s bound and never run while holding the lifecycle
lock, so a dripping `/healthz` cannot stall every caller. `auto_open` is disabled after the explicit
connect, so a connection closed by a cancelled caller cannot be silently reopened by `request()`. The brief keeps the newest 6
sections within 3,500 UTF-8 bytes; the summary is one line capped at 1,200 UTF-8 bytes. All budgets
are measured in bytes with a character-boundary cut, not Python character counts.

`runner/project_runs.with_memory_brief()` appends the block after the task, and `runner/app.py` calls
`ai_memory.brief()` before `_project_cmd` and `ai_memory.record_run()` where the final run record is
assembled. For Codex, the recorded summary is the last `agent_message` (`closing_summary`), because
the full run output concatenates every message and its head would be the opening commentary. Both are skipped unless `binding["confidential"] is False`; a resumed run skips the brief
because its session already holds the context.

## Key decisions and trade-offs

- **Service, not harness integration.** ai-memory's own `setup` writes `~/.local`, `~/.claude`,
  `~/.codex` and a LaunchAgent. That is outside this worktree, would load into sandboxed confidential
  runs, and DSH has no apply-able hook file (its Cordis patch is manual). The runner talks HTTP
  directly, so every provider gets the same behaviour with no per-harness drift.
- **Per-ticket page, not many pages.** The brief is one contiguous recent-history block that fits a
  prompt budget; a page per run would need N reads and a ranking decision the runner does not need.
- **MCP for writes, not the CLI.** The CLI `write-page` cannot pass `workspace`/`project` explicitly (it
  infers scope from cwd) and has no conditional write. `/admin/write-page` writes but has no
  precondition. `memory_write_page` gives both scope and `expected_page_id`.
- **After the task, not before.** The runner's rules must stay first; the memory block is evidence from
  a possibly different provider, so it is appended and explicitly marked as untrusted history.
- **In-card handoff stays AGE-114.** Resumed sessions keep the reply-only rule; this adds cross-card
  knowledge, not a second transcript replay.
- **A per-checkout port and a repo-local data dir.** The port is `49375 + crc32(data_dir) % 200`, so two
  checkouts normally do not share a service; the 200-port range can collide, which the authenticated
  401/403 backoff handles. `AGENTIC_OS_AI_MEMORY_PORT` overrides. A stock ai-memory on 49374 is left
  alone; the wiki and index are gitignored runtime state, and the binary is not committed.
- **Pinned version.** The reviewed contract is ai-memory 3.2.2; the installer defaults to it rather
  than `latest`, so an unassessed MCP schema cannot silently turn memory off through the fail-open path.
- **Zero-LLM path only.** No provider key, no consolidation prompt, no vectors beyond the local
  embedding model that ai-memory fetches on first start.

## Assumptions and risks

- ai-memory 3.2.2's `/mcp` is stateless and accepts `tools/call` directly; verified against the real
  binary on this machine. A future release could change the tool schema — the client fails open.
- The first start downloads a local embedding model (~91 MB of data under `state/ai-memory`). Offline,
  ai-memory falls back to FTS-only; the client does not depend on embeddings.
- `state/ai-memory/` holds prompt-derived summaries for non-confidential projects only. It is
  operator-readable plain markdown; the redaction pass is best effort, not a guarantee.
- Codex review in this sandbox needed a writable `CODEX_HOME` and the repo's nested-sandbox shim; that
  affects how the review ran, not the reviewed code (see the review log).

## Non-goals

- Lifecycle-hook capture, MCP registration or interactive-session capture.
- Project-level decision pages, handoffs, agent messaging or the LLM/dream paths.
- Dashboard UI for the memory pages.
- Dogfooding or confidence claims beyond the recorded test and real-binary evidence.
